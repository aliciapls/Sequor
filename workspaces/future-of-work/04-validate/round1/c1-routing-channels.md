## Findings

### [HIGH] H1 — Digest module API drift breaks integration-suite collection

- **file:line**: `src/sequor/digest/service.py` (exports) vs `tests/integration/test_digest_integration.py:28`, `test_e2e_happy_path.py:30`, `test_e2e_escalation_chain.py:24,208`
- **evidence**:
  `.venv/bin/python -c "import sequor.digest.service as m; print([n for n in dir(m) if not n.startswith('_')])"`
  → exports `DigestService`, `DigestEmailData`, `build_digest_email`, `build_digest_subject`.
  Tests import `gather_digest_data`, `format_digest_email`, `send_digest` (module-level).
  `pytest tests/integration/test_digest_integration.py --collect-only -q` → `ImportError: cannot import name 'gather_digest_data'` … `Interrupted: 1 error during collection`.
- **spec ref**: channel-coordination.md §"Daily Digest Email"; governance: `testing.md` §Audit Mode (collect-only is a merge gate) + `orphan-detection.md` Rule 5 (a collection error blocks the ENTIRE suite, not just the file).
- **impact**: three integration test files cannot be collected; any `pytest tests/integration/` run aborts at collection.
- **recommended fix**: this is a stale-test vs missing-impl drift. The real public surface is the `DigestService` class (`send_digest(tenant_id, account_id)` / `send_all_tenants()`) plus `build_digest_email(data)` / `build_digest_subject(data)`. Either (a) add thin module-level `gather_digest_data(db, tenant_id, account_id, hours)` + `format_digest_email(data)` + `send_digest(...)` wrappers delegating to the class (the tests encode the intended function API), or (b) rewrite the three test files to drive `DigestService`. Pick (a) if the function API is the intended contract; do it in the same PR and re-run collect-only to green.

### [HIGH] H2 — `RoutingOutcome` is an orphan: model + table, zero write sites

- **file:line**: `src/sequor/db/models.py:676` (model) — only other reference is `db/database.py` (schema registration)
- **evidence**: `grep -rln "RoutingOutcome" src/` → `db/models.py`, `db/database.py` only. `grep -rn 'create("RoutingOutcome"' src/sequor/` → no output. `auto_response_accepted`/`auto_response_rejected` (models.py:697-698) never assigned anywhere.
- **spec ref**: message-routing.md §"Outcome Tracking Instrumentation": _"This is not a future feature. It is architected from day 1: Every routing decision logs a RoutingOutcome record at the time of routing."_ Also §"Routing Intelligence Flywheel" moat depends on these records.
- **impact**: the documented compounding-data moat is unimplemented; the nightly aggregation + per-category acceptance thresholds have no source data. Documented behavior the code does not perform.
- **recommended fix**: write a `RoutingOutcome` row at each routing decision (auto-respond / escalate / human-override) in `WhatsAppAutoReplyService.process_message` and the email `AutoReplyService`, and update `auto_response_accepted/rejected`/`resolved_at` when the outcome is known. Add a Tier-2 wiring test asserting a row lands (`facade-manager-detection.md`/`orphan-detection.md` Rule 1-2).

### [HIGH] H3 — HUMAN override: future-message suppression, template, and rejection flag not implemented

- **file:line**: `src/sequor/whatsapp/inbound.py:89,110-111`; `src/sequor/onboarding/app.py:446`; `src/sequor/compliance.py:41`
- **evidence**: `is_human_override` is evaluated per-message on `inbound.body_text` only. The flag is written to the Message (`message_data["human_override"]=True`) but never to the Contact. The webhook guard `if result.get("status")=="created" and not result.get("human_override")` (app.py:446) uses THIS message's detection — so a contact who sends "HUMAN" once, then sends "where is my invoice?", yields `is_human_override=False` and IS auto-responded. No `human_override` template ("A team member will respond shortly") is ever sent; `auto_response_rejected` (RoutingOutcome) is never set.
- **spec ref**: message-routing.md §"2. HUMAN rejection path": _"The contact's future messages are tagged human_override = true and never auto-responded"_, _"The contact receives a template message: 'A team member will respond shortly'"_, _"The auto_response_rejected flag is set in RoutingOutcome"_.
- **impact**: a contact who explicitly requested a human can still receive AI auto-replies on subsequent messages — a compliance-facing behavior (WhatsApp override path) silently not honored beyond the triggering message.
- **recommended fix**: persist a durable override on the Contact (or a ChannelConsent/override record); in both inbound and the auto-reply guard, force-escalate + suppress auto-reply whenever the contact carries the override, not just the current message; send the `human_override` template; write `RoutingOutcome.auto_response_rejected=True`.

### [HIGH] H4 — Entire WhatsApp subsystem has ZERO importing tests

- **file:line**: `src/sequor/whatsapp/{auto_reply,inbound,parser,rate_limiter,sender,signature,utils}.py`
- **evidence**: `grep -rlin "sequor.whatsapp" tests/` → no output. `grep -rlin "whatsapp" tests/` → only `tests/unit/test_classifier.py` (channel string). 48 test files total; none import any `sequor.whatsapp` module. `grep -rln "verify_meta_signature" tests/` → empty. `grep -rln "is_human_override" tests/` → empty.
- **spec ref**: governance `testing.md` §Audit Mode + task rules: _"every new module MUST have ≥1 importing test — zero importing tests = HIGH regardless of 'suite passes'."_ Security: WhatsApp inbound signature MUST be verified — its verifier (`verify_meta_signature`) has no test. Compliance: `is_human_override` false-positive prevention (spec §2) has no test.
- **impact**: seven modules including the webhook signature verifier and the HUMAN-override detector ship untested; regressions in signature verification or override detection are undetectable by the suite.
- **recommended fix**: add Tier-1 unit tests for `verify_meta_signature` (valid/missing/malformed/mismatch), `is_human_override` (exact/starts-with/"human resources"/empty), `parse_meta_webhook_payload`, and a Tier-2 wiring test for the inbound→auto-reply path.

### [HIGH] H5 — Multi-channel deduplication / thread-key linking not wired

- **file:line**: `src/sequor/escalation/thread_key.py` (derive exists) vs zero production callers; `src/sequor/db/models.py:600` (Escalation has no `thread_key`/`channel` column)
- **evidence**: `grep -rn "derive_thread_key" src/sequor/ | grep -v thread_key.py` → only `escalation/__init__.py:11,17` (re-export). No dedup: `grep -rin "dedup\|similarity.*0.7\|48hr" src/sequor/escalation/` → none. Each inbound message creates its own escalation; no cross-channel link.
- **spec ref**: message-routing.md §"Multi-Channel Deduplication" (48hr window, email+phone+name identity, content similarity >70%); channel-coordination.md §"Duplicate Detection Flow" + §"Thread Key Construction" (72hr, same escalation).
- **impact**: a contact reaching out on WhatsApp + email about the same topic produces two independent escalations — the "unified backup view" and duplicate-escalation prevention are absent.
- **recommended fix**: add `thread_key` + `channel` columns to Escalation; compute `derive_thread_key` at escalation-creation; on create, look up an existing pending escalation with the same `thread_key` inside the dedup window and append rather than create. Add a Tier-2 test for the cross-channel same-topic case.

### [HIGH] H6 — Unified Escalation Record missing spec fields; contradictory-response prevention not stored or wired

- **file:line**: `src/sequor/db/models.py:600-640` (Escalation columns); `src/sequor/escalation/service.py:148-176` (ai_summary/routing_reason/suggested_response emailed, not persisted); `service.py:570` (`check_contradiction` has no production caller)
- **evidence**: Escalation model has none of `thread_key`, `channel`, `ai_summary`, `routing_reason`, `suggested_response`, `ai_auto_replies`, `human_replies`. `create_escalation` receives `ai_summary`/`routing_reason`/`suggested_response` but only passes them to `_build_email` — `escalation_data` (service.py:115-124) persists only model columns. `grep -rn "check_contradiction" src/ tests/` → definition + two unit-test calls; zero send-path callers.
- **spec ref**: channel-coordination.md §"Unified Escalation Record" (field list) + §"Contradictory Response Prevention" (`ai_auto_replies`/`human_replies` stored; backup warned before send).
- **impact**: reply-to-resolve context, unified backup view, and contradiction warnings cannot function as specified — the reviewing backup has no stored AI-reply record to be warned against; `check_contradiction` is dead outside tests.
- **recommended fix**: extend the Escalation model (or a linked table) with the spec fields; persist `ai_summary`/`routing_reason`/`suggested_response` at creation; record every AI auto-reply and human reply; call `check_contradiction` from the human reply-send path and surface the warning.

### [HIGH] H7 — DigestService + WeeklyRecap never scheduled (no in-repo trigger)

- **file:line**: `src/sequor/digest/service.py:109` (`send_all_tenants` — "entry point for scheduler"); `src/sequor/email/templates.py:297` (`build_weekly_recap_email`)
- **evidence**: `grep -rn "DigestService\|send_all_tenants" src/sequor/ | grep -v digest/service.py` → only `digest/__init__.py` re-export. `grep -rn "build_weekly_recap" src/sequor/ | grep -v templates.py` → only `email/__init__.py` re-export. No scheduler/cron/handler instantiates either.
- **spec ref**: channel-coordination.md §"Daily Digest Email" (_"Every morning, the account owner receives a digest email"_) + §"Weekly Recap Email".
- **impact**: the daily digest and weekly recap builders exist but are never invoked in-repo, so the promised emails are not sent by this codebase.
- **note / caveat**: an out-of-repo cron could call `send_all_tenants`; deploy/cron config is outside this cluster's spec scope. If such a trigger exists it belongs in `deploy/` and should be cited. Absent that, this is unshipped behavior.
- **recommended fix**: wire `DigestService.send_all_tenants()` and the weekly-recap send into the escalation scheduler (`escalation/scheduler.py`) or a documented cron entrypoint; add an integration test that asserts a digest send for an active account.

### [MED] M1 — WhatsApp required template set + pool tracking not implemented

- **file:line**: `src/sequor/whatsapp/auto_reply.py:351` (`template_name="acknowledgement"`)

### [MED] M2 — Per-user WhatsApp 6s session throttle unenforced; config field is a documented-but-unused stub

- **file:line**: `src/sequor/config.py:67` (`whatsapp_user_rate_limit_seconds: float = 6.0`); `src/sequor/whatsapp/rate_limiter.py:42`

- **spec ref**: message-routing.md §"Rate Limits (WhatsApp-Required)": _"Session messages: 1 per 6 seconds to same user"_ (Error 131056). Governance: `zero-tolerance.md` Rule 3c (documented setting with zero consumers = silent-fallback class).
- **recommended fix**: enforce a per-recipient minimum interval keyed on `to`, consuming `whatsapp_user_rate_limit_seconds`; add a unit test that two sends to the same user within 6s are spaced/blocked.

### [MED] M3 — First-contact consent recorded AFTER message creation, not before processing

- **file:line**: `src/sequor/whatsapp/inbound.py:97-129` (Message created at step 5; `_ensure_consent` at step 6)
- **evidence**: `_process_single` creates the Message record (`inbound.py:113`) and then calls `_ensure_consent` (`:125`). HUMAN detection + session check also run before consent exists.
- **spec ref**: message-routing.md §"1. Opt-in recording at first contact": _"No message processing begins until consent is recorded."_
- **recommended fix**: record `ChannelConsent` for a first-seen contact before message persistence/classification, or document/adjust the spec if store-then-consent is the intended shipped order (per `spec-accuracy.md`, code and spec must agree).

### [LOW] L1 — Session-window "latest message" assumes list ordering

- **file:line**: `src/sequor/whatsapp/inbound.py:214-217`
- **evidence**: `_check_session_expired` does `recent = await self._db.list("Message", {...})` then `latest = recent[0]` with no explicit `order_by received_at DESC`. Correctness depends on the CRUD layer's default ordering.
- **impact**: if `list` is not ordered newest-first, the session-expiry decision can read an arbitrary prior message. Not a spec assertion; correctness/robustness.
- **recommended fix**: order by `received_at DESC` (or `MAX(received_at)`) explicitly.

### [LOW] L2 — `create_escalation` passes `account_id`, absent from Escalation model (cross-cutting)

- **file:line**: `src/sequor/escalation/service.py:119` vs `src/sequor/db/models.py:600-640`

- **note**: the Escalation data-model is `specs/data-model.md`'s authority (outside this cluster). Flagged for the data-model cluster to adjudicate; verify whether the unknown key is silently dropped (silent-fallback risk).

## Summary

Counts by severity: **HIGH 7, MED 3, LOW 2** (0 CRIT).

Five most important:

1. **H1** — Digest API drift (`gather_digest_data`/`format_digest_email`/`send_digest` missing) → `pytest --collect-only` ImportError aborts the whole integration suite.
2. **H2** — `RoutingOutcome` is an orphan (model+table, zero write sites) though the spec says it is "architected from day 1"; the routing-flywheel moat has no source data.
3. **H4** — Entire `sequor.whatsapp/*` subsystem (7 modules incl. `verify_meta_signature` and `is_human_override`) has zero importing tests.
4. **H3** — HUMAN override only suppresses the triggering message: no persistent contact flag, no `human_override` template, no `auto_response_rejected` — future messages from a contact who asked for a human are still auto-replied.
5. **H5/H6** — Multi-channel dedup + unified escalation record + contradictory-response prevention are unwired: `derive_thread_key`/`check_contradiction` exist but have zero production callers; Escalation model lacks `thread_key`/`channel`/`ai_summary`/`ai_auto_replies`/`human_replies`.
